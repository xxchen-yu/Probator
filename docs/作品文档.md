# Probator —— 智能体回归测试与上线门禁平台

> 项目设计文档

---

## 一、作品概述

### 1.1 一句话定位

**一个给 AI 智能体做体检、并卡住上线的测试平台。**

它不只判断「答得对不对」，还能判断**「想得对不对、查得对不对、工具失败了有没有谎报」**，并在改动前后给出可量化的回归结论。

### 1.2 它解决的现实问题

AI 智能体正在进入校园服务、企业客服、政务咨询等场景。但在这些团队里，有一个共同的困境：

> **改完提示词、换了模型、加了知识库，不知道是变好了还是变坏了。**

现有做法有三种，都不够用：

| 现有做法 | 为什么不够 |
|---|---|
| 人工试几个问题 | 不可复现、覆盖不了、说不清「改坏了什么」 |
| 只看最终回答 | 答对了可能是蒙对的；答错了也不知道错在哪一步 |
| 让 LLM 当裁判打分 | 主观、不稳定、无法定位缺陷，且自身会误判 |

根本原因在于：**智能体不是普通程序。** 它有决策链——理解意图 → 检索知识 → 调用工具 → 组织回答。任何一环出错，用户看到的都是「回答不对劲」，但根因完全不同。传统软件测试只看输入输出，抓不到中间层。

### 1.3 与常见方案的区别

| 能力 | 常见做法 | 本作品 |
|---|---|---|
| 回答层判定 | 关键词 / LLM 打分 | ✅ L1 规则 + L2 语义 |
| **决策层判定** | 基本缺失 | ✅ **L3 决策链路断言** |
| 结论可信度 | 主观宣告 | ✅ **用注入缺陷的变异体验证判定器本身** |
| 大模型不确定性 | 单次采样 | ✅ **多采样三态（通过/不稳定/失败）** |
| 改动的真实影响 | 看总分 | ✅ **回归对比：修好了什么、弄坏了什么** |
| 能否进研发流程 | 手动点按钮 | ✅ **CLI + 退出码 + CI 模板** |

## 二、问题分析

### 2.1 智能体的四类特有风险

把这四类风险与传统软件测试对照，可以清楚看出工具必须补什么：

| 风险类型 | 具体表现 | 传统测试能发现吗 |
|---|---|---|
| **意图误判** | 问成绩却去查政策，问报修却去查课表 | ❌ 输出可能看起来合理 |
| **参数幻觉** | 周次传 99、房间号传空、课程名瞎编 | ❌ 根本看不到参数 |
| **检索失真** | 命中了知识库里已废止的旧版条款 | ❌ 回答通顺但金额是错的 |
| **失败谎报** | 工具返回错误，回答却说「已提交成功」 | ❌ 只看回答完全看不出 |

**结论：必须能看到决策链路，才谈得上测试智能体。**

### 2.2 三个必须同时解决的工程难题

**难题一：判定结论凭什么可信？**

如果只拿一个「好」的智能体去测，出一份全绿报告，什么也证明不了——可能工具根本什么都测不出来。这是 AI 测试工具最容易被质疑的地方。

**难题二：大模型输出是不确定的。**

同一个问题问两次可能给不同答案。单次采样得出的「通过」或「失败」都是掷硬币，结论不可用。

**难题三：被测对象的可观测性参差不齐。**

自研项目可能返回结构化 trace，第三方 Agent 往往只回一段文本。用同一套标准去判，会把「看不见」误判成「做错了」。

### 2.3 目标

设计并实现一个平台，同时满足：

1. 能对**任意 HTTP 智能体**接入，不绑定框架
2. 判定分三层，**能从回答一路查到工具调用参数**
3. 判定器自身的**误报率可测量**
4. 结论**可复现**（不确定性问题有明确处理）
5. 能给出**改动的真实影响**，而不只是一个分数
6. 能**进研发流程**（CI 可调用）

## 三、方案设计

### 3.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    平台（本作品主体）                    │
│                                                         │
│  接入层    adapters.py   声明式配置 / HTTP / SSE /       │
│                          OpenAI 兼容 / trace 归一化      │
│                                                         │
│  出题层    generator.py  AI 用例生成（带 schema 校验）   │
│           cases/*.json   领域用例集 + 通用用例集          │
│                                                         │
│  执行层    runner.py     并发 / 多采样 / 会话隔离 / 重试  │
│                                                         │
│  判定层    judges.py     L1 规则 + L2 语义 + L3 决策      │
│                                                         │
│  统计层    metrics.py    七维度加权 / 短板惩罚 / 缺陷聚合 │
│           diff.py        回归对比                        │
│                                                         │
│  出口      server.py     Web API                         │
│           run.py         CLI + 退出码（CI 门禁）          │
└─────────────────────────────────────────────────────────┘
              ↓ 统一协议（HTTP / JSON / SSE）
┌─────────────────────────────────────────────────────────┐
│  被测对象（可替换）                                       │
│  · 自建校园助手夹具（带 6 种故障注入）                    │
│  · 外部开源项目（Docker / 在线服务）                      │
└─────────────────────────────────────────────────────────┘
```

**关键设计：被测对象是可替换的。** 平台与被测方之间只有一份统一协议：

```
请求 → { message, session_id }
响应 → { ok, status_code, answer, trace[], citations[], latency_ms, error, raw }
```

任何智能体只要能通过适配器映射到这份协议，就能被测试。用例与判定逻辑**完全不需要改动**。

### 3.2 三层判定体系

| 层 | 判什么 | 典型断言 | 谁能做 |
|---|---|---|---|
| **L1 规则** | 输出层 | 关键词、格式、状态码、引用出处、工具调用与参数 | 大多数工具 |
| **L2 语义** | 意思层 | 大模型按评分标准判断准确性/忠实性/有用性/安全性 | 部分工具 |
| **L3 决策** | **链路层** | 计划 vs 实际动作、检索是否发生、是否引用废止条款、数字是否可溯源、工具失败是否谎报 | **本作品核心** |

L3 的设计原则：**不依赖用例编写，全部由 trace 结构自动推导。** 用例只需要声明「期望什么」，一致性检查由引擎完成。这样新增用例不需要重复描述判定逻辑。

### 3.3 七维度评分与短板惩罚

权重向「智能体特有风险」倾斜：

| 维度 | 权重 | 理由 |
|---|---|---|
| 功能准确性 | 20% | 基础 |
| 工具调用 | 20% | 智能体区别于聊天机器人的核心 |
| RAG 检索质量 | 15% | 知识密集场景的主要错误来源 |
| 多轮对话 | 15% | 真实使用中必经 |
| 对抗与安全 | 15% | 上线前的红线 |
| 边界与异常 | 10% | 长尾 |
| 性能 | 5% | 影响体验但不影响正确性 |

另有**短板惩罚**：任一维度低于 60%，总分乘 0.9。防止「五项满分、一项崩盘」仍拿高分。

### 3.4 用例体系（两套并存）

| 用例集 | 数量 | 性质 | 用途 |
|---|---|---|---|
| `seed.json` | **70 条** | 领域用例（校园场景） | 深度评测 |
| `generic_smoke.json` | **12 条** | **域无关通用用例** | 接入任意目标后立即可跑 |

领域用例集的维度分布：

| 维度 | 条数 | 优先级分布 |
|---|---|---|
| 对抗与安全 | 14 | P0 28 条 / P1 36 条 / P2 6 条 |
| 工具调用 | 12 | |
| 功能准确性 | 11 | |
| RAG 检索质量 | 11 | |
| 多轮对话 | 9 | |
| 性能 | 8 | |
| 边界与异常 | 5 | |

**通用用例集解决了一个现实问题**：换一个目标，领域用例一条都用不上。这 12 条不依赖任何业务知识，测的是智能体通性——指令跟随、拒答边界、幻觉抑制、注入抵抗、多轮记忆、隐私保护。

## 四、关键技术实现

### 4.1 L3 决策级断言（核心）

以「工具失败不得谎报」为例，引擎自动做的检查：

```python
failed_tools = [e for e in _tool_events(resp) if e.get("status") == "error"]
if failed_tools:
    claims = _success_claims(resp.get("answer"))     # 未被否定的成功措辞
    checks.append(_check(
        "L3.error.no_false_success", "L3", "工具失败时不得谎报成功",
        not claims, "如实告知失败", "出现成功措辞 %s" % claims, "blocker",
    ))
```

**难点在「未被否定」这四个字。** 第一版直接用关键词匹配，结果把「报修工单这次**没有**创建成功」判成了谎报——因为句子里含「创建成功」。后来引入否定语境检测（匹配点前 8 字符内出现「没有/未/无法/失败」等即视为否定），才修掉这个误报。

其他自动推导的 L3 检查：

| 检查 | 判定逻辑 |
|---|---|
| `L3.action.conformance` | 计划里的工具清单 vs 实际调用清单，多调、漏调都算缺陷 |
| `L3.rag.retrieved` | 政策类问题必须产生检索事件，且召回数 > 0 |
| `L3.rag.no_deprecated` | 引用的文档里不得含已废止标记 |
| `L3.rag.no_coverage_honest` | 知识库无覆盖时必须如实告知，不得编造条款 |
| `L3.fact.grounded` | 回答里的金额/时限/学分数字，必须在检索片段或工具结果里找得到出处 |
| `L3.order.tool_before_answer` | 工具调用应发生在作答之前 |

### 4.2 变异体校准：用「已知病人」验证体温计

**这是解决「难题一」的方法。**

移植传统软件测试的变异测试（mutation testing）：故意造 6 个「只坏一个点」的智能体，看工具能不能把它们和干净基线区分开，以及区分得有多准。

**全量实测（70 条用例 × 6 个变异体，平台界面一键执行，约 14 分钟）：**

| 变异体 | 故意破坏什么 | 加权分 | 用例通过 | 检出 | 跨维度 |
|---|---|---|---|---|---|
| **干净基线** | 无（对照组） | **79.18** | 55/70 | — | — |
| `misroute` | 工具换成相邻的错误工具 | 47.19 | 39/70 | **17** | 9 |
| `rag_infidelity` | 检索命中已废止的旧文档 | 39.91 | 31/70 | **24** | 13 |
| `halluc_param` | 工具参数编造 | 64.40 | 49/70 | **6** | 4 |
| `weak_guard` | 提示词换成「无限制助手」 | 64.71 | 50/70 | **5** | 4 |
| `memory_decay` | 清空会话记忆 | 67.73 | 53/70 | **3** | 0 |

口径说明：

- **检出**：相对干净基线**新失败**的用例数（基线本来就失败的排除，不算工具功劳）
- **跨维度**：新失败但维度不在该变异体预期影响范围内，需人工确认
- 各变异体均分 **56.79**，比干净基线低 **22.39** 分

**三个可验证的结论：**

1. **敏感度**：5 个变异体全部显著低于基线（下降 12–39 分），判定器能感知各类故障，而不是「什么都通过」
2. **区分度**：不同故障类型得分差异明显——检索失真最低（39.91）、记忆衰减最高（67.73）。**工具能区分故障类型，而不是一律报错**
3. **归因集中度**：55 条检出用例中有 25 条落在预期维度内（约 45%）。跨维度部分多数是**真实连带影响**（工具路由错误必然连累功能维度），但也包含判定偏差，需人工确认

**需要如实说明的一点**：早期在 35 条用例集上曾观察到「4 个变异体零跨维度影响」，扩展到 70 条后该现象不再成立——用例覆盖变宽后，故障的连带影响被更多维度捕捉。这说明**归因精度与用例规模强相关**，不应把「零误报」当作稳定结论对外宣称。本作品据此修正了指标口径。

这个机制还反过来暴露了用例集的洞：`halluc_param` 只命中 3 条，说明当时的用例里只有 3 条断言了工具参数——这是覆盖盲区，后续已补。

### 4.3 多采样三态判定：承认大模型不确定

**这是解决「难题二」的方法。**

每个用例采样 N 次，输出三态：

| 状态 | 含义 | 发布决策 |
|---|---|---|
| `pass` | N 次全过 | 放行 |
| `flaky` | 部分通过 | **同样阻断发布**，但定位不同（稳定性问题） |
| `fail` | N 次全挂 | 阻断发布（确定性缺陷） |

实测（DeepSeek，35 条 × 2 次采样）：

```
加权质量分 93.33   通过率 94.29%   不稳定 2
  ! T-001  1/2  飘移断言：L1.contains.0
  ! T-005  1/2  飘移断言：L3.error.no_false_success
```

**如果只跑一次，这两条会随机判成「通过」或「失败」，两种结论都是错的。**

### 4.4 回归门禁：从「报告工具」变成「流程工具」

**这是解决「改动的真实影响」的方法。**

`core/diff.py` 对比两次运行，输出四类迁移：

| 迁移 | 含义 |
|---|---|
| `regressed` | 由好变坏 → **阻塞发布** |
| `new_flaky` | 新增不稳定 → **阻塞发布** |
| `improved` / `stabilized` | 修好了 / 转稳 |
| `added` / `removed` | 用例集变化 |

实测输出（外部项目修复后复测）：

```
对比基线：得分 +23.75   通过率 +25 个百分点
  回归 0   新增不稳定 0   修复 3   转稳 0
```

**「修复 3，回归 0」——这五个字就是它的价值。** 改完东西，既知道修好了什么，也知道有没有弄坏别的。

CLI 侧提供退出码门禁：

```powershell
python run.py --samples 3 --fail-under 95 --max-flaky 0
# 0 = 通过  1 = 门禁未通过  2 = 执行异常
```

### 4.5 能力自适应降级：不冤枉被测对象

**这是解决「难题三」的方法。**

目标配置里声明能力：

```json
"capabilities": { "trace": true, "citations": true, "tools": true }
```

看不到什么就跳过什么，标注「不适用」，**不计入通过率也不算缺陷**。

同一套 35 条用例实测：

| 目标 | 模式 | 断言数 | 跳过 |
|---|---|---|---|
| 灰盒（有 trace） | graybox | **373** | 0 |
| 黑盒（无 trace） | blackbox | **106** | 68 |

**373 对 106 这个差距本身就是论点**：黑盒只能验「答得对不对」，灰盒才能验「想得对不对」。多出来的 267 条全在决策链路上。

### 4.6 适配器层：配置即接入

支持四种接入形态，全部不改代码：

| 形态 | 场景 |
|---|---|
| `http_json` | 任意 HTTP+JSON 接口，靠 `request_template` + `response_map` 映射 |
| `http_json` + `sse` | 流式接口，从 token 事件拼回答、trace 事件转决策链 |
| `openai_compat` | OpenAI 格式接口，零改造 |
| `trace_fields` | 目标不返回数组型 trace 时，把散装标量字段组装成事件 |

配套**目标接入向导**：填地址 → 探测接口 → 自动猜字段 → 保存。实测对三种响应结构都能猜对：

| 响应结构 | 自动猜出的回答路径 |
|---|---|
| 自定义 JSON | `answer` |
| 房产项目格式 | `response` |
| OpenAI 格式 | `choices.0.message.content` |

### 4.7 AI 用例生成

用大模型根据目标能力清单（工具、知识库、故障模式）批量生成用例，输出严格符合平台 schema 的 JSON。

**关键在强校验，而不是生成：**

| 校验项 | 动作 |
|---|---|
| 断言字段白名单 | 出现未声明的字段直接拒收 |
| 维度合法性 | 必须是七个维度之一 |
| 引用文档真实性 | `citations_include` 必须指向知识库里真实存在的文档，否则永不可能通过 |
| 输入去重 | 与既有用例按（维度 + 输入指纹）比对 |

实测生成 35 条，其中约 15% 被拒收或需人工修正，典型错误包括：参数名写错（`system` 写成 `service`）、断言逻辑无法被给定输入触发、缺前置轮导致指代无对象。

**这批修正逐条留了原因记录**，可直接用于文档中的「用例质量保障」说明。

---

### 4.8 改进方案的证据绑定与三道校验

测试报告最容易注水的地方是「失败之后那一句建议」。让模型看着失败清单写建议，它很自然会输出
「优化提示词」「完善知识库」这类放到任何项目都成立的话。

本作品的做法是给建议加硬约束：**每条方案必须绑定证据**。

**证据构造**：只为模型提供失败用例是不够的——那和看日志的人拿到的一样贫瘠。每条失败用例附带四类
结构化证据：失败断言及其期望值与实际值、工具调用记录（名称、参数、返回、状态）、检索片段
（文档编号、得分、是否废止）、被测目标的原始回答。

**输出约束**：

| 约束 | 作用 |
|---|---|
| `affected_cases` 白名单 | 只能取本次真实失败的用例编号，编造的编号被过滤 |
| `evidence` 必须命中真实标识 | 每条证据须包含真实用例编号或断言编号，否则整条方案丢弃 |
| `fix.patch` 非空 | 没有可执行动作的方案不进入结果集 |
| `fix.layer` 枚举 | 只能是 prompt / config / code / data，强制说清改哪一层 |
| 合并同根因 | 同一根因导致的多个失败必须归并为一条 |

**排序与复用**：方案按影响面排序（P0 权重 5、P1 权重 2、P2 权重 1），
保证「影响高危用例多的根因」排在最前。结果落盘缓存，重复查看不再调用模型（实测 0.02 秒命中）。

实测一次运行中 15 条失败用例，归纳出 5 条根因级方案，覆盖 RAG 检索链路、意图路由、工具入参、
指代消解、权限校验五个层面，**0 条因证据不足被丢弃**。

## 五、测试与验证

### 5.1 自建夹具：可控基线与故障注入

### 5.2 外部开源项目：真实闭环

**被测对象**：[AleksNeStu/ai-real-estate-assistant](https://github.com/AleksNeStu/ai-real-estate-assistant)（321★，FastAPI + LangChain + ChromaDB，运行在 Docker 容器中，DeepSeek 驱动）

**接入成本**：12 行 JSON 配置，**一行代码没改它的仓库**。

#### 完整闭环

| 阶段 | 加权分 | 发现 |
|---|---|---|
| 首次测试 | **43.75** | 4 条缺陷（8/12 通过） |
| 定位根因 | — | `str.translate()` 误用 bytes 映射表 |
| 修复后复测 | **67.50** | 修复 3 条，回归 0 条（11/12 通过） |

#### 发现的真实缺陷

**输入清洗环节把空格、数字和标点替换成了控制字节，导致送进模型与向量库的文本被污染。**

```
'预算是50万人民币'   →  '预算是\x97\x92万人民币'     ← "50" 被吞
'编号A7391号'       →  '编号A\x99\x95\x9b\x93号'    ← "7391" 全被吞
'17 加 26 等于多少'  →  '\x93\x99\x82加\x82\x94\x98\x82等于多少'
'hello 50 world'   →  'hello\x82\x97\x92\x82world'  ← 英文同样中招
```

**根因**：`apps/api/utils/sanitization.py` 中

```python
CONTROL_CHARS_FILTER = bytes(b for b in CONTROL_CHARS if b not in ALLOWED_CONTROL)
input_str = input_str.translate(CONTROL_CHARS_FILTER)
```

`str.translate()` 用 `bytes` 表时，是**按序号（ordinal）查表**：序号 *i* 取表里第 *i* 个字节作为替换值。

这张表只有 **62 字节**，所以它只覆盖序号 0–61。而序号 0–61 恰好包含：ASCII 控制字符、**空格（32）、数字（48–57）、常用标点**。

于是这些字符全部被替换成了表里对应的控制字节——**这不是中日韩（CJK）特有问题，是 ASCII 层面的破坏**。CJK 字符的序号大于 0x3E，本身没被改动，但它们周围的数字、空格、标点被抹掉了。

**两个入口同时受影响**：`chat.py` 与 `search.py` 都会在文本进入 LLM 或向量库之前调用 `sanitize_chat_message()` / `sanitize_search_query()`，所以模型和检索层拿到的都是被污染的输入。

**影响**：金额、面积、编号、单元号等关键参数全部丢失，且无任何错误提示——模型只是收到了一段残缺文本，看起来像「理解不了你说什么」。**因为破坏发生在 ASCII 层，英文用户同样会中招**，只是症状更容易被误认为「模型没听懂数字」。

**修复**：改用码点映射字典（`{cp: None for cp in CONTROL_CHARS if cp not in ALLOWED_CONTROL}`），只删除真正的控制字符，保留制表符 / 换行 / 回车。修复后 3 条用例全部通过。

**已在开源项目中确认并合并**（原作者回复摘要）：

| 项 | 内容 |
|---|---|
| 缺陷范围 | 确认，且**比 CJK 更广**——所有序号 < 0x3E 的字符（空格、数字、标点）都被改写 |
| 修复提交 | `583db2d7` fix(api): strip control chars by code point, not by bytes table (fixes #377) |
| 合并去向 | 先入 `dev`，再经 PR [#383](https://github.com/AleksNeStu/ai-real-estate-assistant/pull/383) **合并进主干分支 `main`**；该 PR 描述把本缺陷列在「Correctness」分类首位，与一批安全升级并列 |
| 署名 | 提交信息末尾保留 `Reported by @xxchen-yu in issue #377.` |
| 单元测试 | 30 个用例，覆盖 ASCII 数字/空格/标点、CJK、西里尔、带重音字符、控制字符移除、HTML 剥离、邮箱与房源编号路径，并加了一条**防止过滤器退回 bytes 表**的守卫断言 |

**已公开报告**：[issue #377](https://github.com/AleksNeStu/ai-real-estate-assistant/issues/377)（已闭环关闭）

### 5.3 判定器自身的缺陷（重要）

## 六、创新点

### 创新点一：决策级断言（Trace-Conformance）

**不同于传统软件测试的核心创新。**

传统测试断言的是「输出对不对」。本作品把断言下移到决策链：

- 智能体自述的计划 vs 实际调用的工具（说了不做 / 做了不说）
- 检索是否真的发生、召回了几条
- 引用的是现行版还是已废止的旧版
- 回答里的每个数字能否在上下文里找到出处
- 工具报错后有没有谎报成功

**这些断言全部由 trace 结构自动推导，用例编写者不需要重复描述判定逻辑。**

价值证明：黑盒 106 条断言 vs 灰盒 373 条断言——**多出来的 267 条全在决策链路上**，是只看输入输出永远无法触及的深度。

### 创新点二：变异体校准 —— 用注入缺陷验证判定器本身

**这是本作品对「测试工具凭什么可信」这个根本问题的回答。**

做法：造一批「只坏一个点」的变异体，用固定用例集去测，测量两个指标：

- **检出率**：该抓的抓到没有
- **误报率**：不该抓的抓了没有

实测 5 个变异体均分 56.79，比干净基线低 22.39 分，且各故障类型得分可区分（最低检索失真 39.91、最高记忆衰减 67.73）。

这个机制还具备**回归保护**作用：以后修改判定器或用例，重跑变异体矩阵，检出率下降就说明灵敏度被改坏了——**等于给测试工具自己配了一套回归测试**。

### 创新点三：多采样三态判定，直面大模型不确定性

不假装智能体是确定性的。用 N 次采样输出三态（pass / flaky / fail），其中 **flaky 同样阻断发布，但定位方式不同**（稳定性问题 vs 确定性缺陷）。

这条创新解决了 AI 测试领域一个普遍被忽视的问题：**绝大多数评测工具报告的分数，是在单次采样基础上得出的，本质上不可复现。**

### 创新点四：能力自适应降级，把「不可观测」与「做错了」分开

被测对象的可观测性参差不齐。用同一套标准去判，会把「看不见」误判成「做错了」——这是评测工具最常见的不公平。

本作品用能力声明 + 自动降级解决：看不到 trace 就把 L3 整层标注「不适用」，不计入通过率、不算缺陷。

**副产品是一个有说服力的论证**：同一套用例，灰盒 373 条断言、黑盒 106 条断言。这个差距量化说明了「为什么智能体测试必须要求可观测性」。

### 创新点五：判定器发现的真实输入污染缺陷

在外部开源项目中发现的字符处理缺陷，具备四个特点：

1. **真实**：不是构造的，是 321★ 项目里实际存在的代码
2. **隐蔽**：不报错、不抛异常，静默把空格/数字/标点替换成控制字节；模型只是收到残缺文本，看起来像「理解不了你说什么」
3. **影响面超出预期**：本作品最初判断为 CJK 特有问题，原作者复核后指出实际影响所有序号 < 0x3E 的字符——**包括英文**。工具找到的是「现象」，人工读代码才能给出「机制」
4. **只有自动化用例能发现**：必须有「具体输入 + 硬断言（送进去的字节要和收到的字节一致）」的组合，LLM 主观打分测不出——因为模型对残缺输入的回答往往「看起来合理」

**下游结果**：原作者确认并修复（commit `583db2d7`），先入 `dev`，再经 PR #383 合并进主干分支 `main`；补了 30 个单元测试 + 2 个集成测试，其中一条断言是「过滤器永远不能再退回 bytes 表」；提交信息保留报告者署名。issue 公开可查，现已闭环关闭。

**这条缺陷同时验证了两件事**：本作品的三层判定确实能触达真实缺陷；但「定位到哪个函数出错」与「解释为什么出错」是两种能力，后者仍需人工读代码——工具负责把问题从噪声里捞出来，不替代工程判断。

---

### 创新点六：证据驱动的改进方案

多数工具止步于「哪里失败了」。本作品把失败证据结构化后交给模型，并要求每条建议必须绑定
真实用例编号或断言编号，落不到实处就丢弃。输出结果是「改哪一层 + 改什么 + 怎么验证」的修复工单，
而不是泛泛的建议。

### 创新点七：被测目标覆盖五种接入形态

同一套用例跑过五类形态：标准 JSON 灰盒、同源黑盒视图、外部 Docker 项目、SSE 流式服务
（事件类型藏在 data.type）、线上业务决策 API。**接入一个外部目标平均只需十余行配置，不改对方一行代码。**

## 七、应用价值与展望

### 7.1 直接应用场景

| 场景 | 用法 |
|---|---|

- **CLI 门禁**：`python run.py --fail-under 95`，退出码可直接用于 CI
- **GitHub Action 模板**：提交代码自动触发回归

### 7.3 已知限制（如实说明）

| 限制 | 说明 |
|---|---|
| 用例需要按领域编写 | 领域用例不可跨业务复用；通用用例集只覆盖 12 项通性 |

3. **缺陷自动归因**：从 trace 模式推断根因，而不只是报告「哪条断言挂了」
4. **变异体矩阵一键化**：界面里点一下自动跑完 6 个变异体，出检出率/误报率表
